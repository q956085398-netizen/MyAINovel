# 工笔整体验收修复与终验

Part of #54；亦属于 #1 总地图的整体收口工作。

发布工单：[ #76 整体验收修复与终验](https://github.com/q956085398-netizen/MyAINovel/issues/76)，标签 `ready-for-agent`。

## Problem Statement

实现工单关闭后，作者仍不能确认工笔可以安全用于日常创作。2026-09-27 的整体验收发现：保存等待期间继续输入再切章，新增文字可能没有保存却被下一章覆盖；更换库位置后，已打开的拆书稿、构思项目和书写项目仍可能指向旧库；伏笔、期待线与主线里程碑没有总规格承诺的待打磨状态与顶部便笺。

当前 370 项后端测试、46 项前端测试、生产构建及 Windows 安装包构建均通过，但这些证据没有覆盖上述完整页面行为，也不能替代真实 Windows 应用的新旧库及重启验收。作者需要的是能保住最新文字、明确当前库归属、兑现已有内容状态合同的日常创作工具，以及有证据的整体通过结论。

## Solution

让所有会替换或卸载编辑器的用户导航，在最新编辑内容保存完成后才继续；未保存、冲突或失败时保留原编辑器和文字。更换库位置作为一次完整的工作区切换，先处理旧库缓冲，再让所有板块、搜索、当前项目和速记只作用于新库，并隔离旧库迟到的响应。

按 #54 已有“任意内容对象可待打磨”约定，为伏笔、期待线和主线里程碑补齐独立待打磨状态、完整便笺和退出后的原分类及次序恢复。保持原文件为唯一数据源，不以既有待埋、兑现或待落地状态代替待打磨。

修复后在既有底层测试之外，补上真实页面行为回归，最后用旧库完整副本与干净新库，在 Windows 应用中完成六条跨板块流程及关闭重开验证。交付明确区分代码修复通过、页面回归通过和实机终验通过。

## User Stories

1. As an author, I want every character entered before leaving a chapter to be preserved, so that changing chapters never silently loses my writing.
2. As an author, I want typing during a save request to remain part of the unsaved buffer until persisted, so that a delayed save response cannot mark newer text as safely saved.
3. As an author, I want chapter navigation to continue only after the latest text is saved, so that the next chapter cannot replace an unsaved revision.
4. As an author, I want returning to the project list to use the same save protection, so that leaving the editor is as safe as changing chapters.
5. As an author, I want opening a global search result to preserve the current writing first, so that retrieval never discards work in progress.
6. As an author, I want book-analysis editor navigation to follow the same safety rule, so that notes receive the same protection as manuscript prose.
7. As an author, I want a save conflict to keep me at the current object with my text intact, so that I can resolve external edits deliberately.
8. As an author, I want save failure to leave the current editor available for retry, so that temporary disk problems do not become lost content.
9. As an author, I want repeated navigation actions during saving to produce a coherent destination, so that overlapping requests cannot load unrelated content or clear my buffer.
10. As an author, I want navigation protection to coexist with normal typing and autosave, so that the fix does not turn routine writing into repeated confirmation dialogs.
11. As an author, I want changing library location to finish or resolve my current saves first, so that a workspace change cannot abandon existing edits.
12. As an author, I want cancelling a folder choice or a blocked library change to keep the old library active, so that the interface and write destination stay consistent.
13. As an author, I want an empty new library to show its own empty state in every section, so that an old book never appears to belong to the new library.
14. As an author, I want opened book-analysis notes and ideation and writing projects to belong to the displayed library, so that further edits always reach the intended files.
15. As an author, I want old-library scan and search responses to be ignored after switching, so that late results cannot repopulate the new workspace with old objects.
16. As an author, I want current-project and resume-work entries to be validated against the active library, so that shortcuts cannot silently reopen a project from another library.
17. As an author, I want quick notes to link to the active library's current project and chapter, so that the capture flow remains usable after switching libraries.
18. As an author, I want search destinations and pending navigation requests from the old library to be invalidated, so that a delayed jump cannot undo my workspace change.
19. As an author, I want existing conversation history preserved while stale document targets are detached, so that changing libraries does not erase my conversations or allow adoption into an old editor.
20. As an author, I want foreshadows to support an independent 待打磨 state, so that unfinished thinking does not require changing their planting or recovery status.
21. As an author, I want expectation and goal lines to support 待打磨, so that refining a line does not alter its category, horizon, or fulfillment state.
22. As an author, I want mainline milestones to support 待打磨, so that a provisional milestone can remain in its narrative context while receiving attention.
23. As an author, I want these pending objects to appear as complete notes at the top of their own page, so that their filled content is visible without repeatedly opening dialogs.
24. As an author, I want completing a pending note to return it to its original classification and narrative order, so that temporary attention never rearranges my plan.
25. As an author, I want the pending section to disappear when empty, so that an unused state does not occupy page space.
26. As an author, I want pending status persisted in the original object's data, so that there is no second note copy to diverge from my work.
27. As an author, I want existing YAML data without pending fields to remain readable without migration, so that the feature does not force me to rewrite old projects.
28. As an author, I want manually added fields and unrelated table entries preserved during state changes, so that refining one object does not erase other planning data.
29. As an author, I want unreadable or externally changed structured data to stop unsafe writes, so that the application never silently repairs or replaces content it cannot safely understand.
30. As an author, I want identical milestone titles to remain distinguishable, so that marking one milestone never changes another.
31. As an author, I want a complete legacy-library copy and a clean new library tested in Windows, so that compatibility and first-use behavior are both demonstrated.
32. As an author, I want card browsing, social graphs, map graphs, settings, editor actions, and palette switching verified as complete workflows, so that separately passing modules do not hide integration failures.
33. As an author, I want application restart to preserve settings, layouts, pending status, order, and saved prose, so that daily use remains reliable across sessions.
34. As an author, I want untouched creative files checked before and after acceptance, so that browsing and cancelled previews cannot silently change my library.
35. As an author, I want keyboard navigation, focus visibility, reduced motion, and common laptop window sizes checked, so that the complete application remains usable in my normal environment.
36. As an author, I want acceptance reports to state what was actually executed and what remains unverified, so that I can trust the completion status of the overall work.

## Implementation Decisions

- 延续 ADR 0002 的文件唯一来源、ADR 0004 的原子写与内容指纹约定，以及既有大纲和桥段的人工次序纪律。本规格不把总合同缩小为仅支持 Markdown 对象。
- 编辑器保存与应用导航之间建立统一的“可安全离开”约定，优先整合现有保存入口与搜索导航守卫。一次保存请求成功只证明该请求的内容快照落盘，不能单独证明当前编辑器已经没有未保存内容。
- 使用最新编辑版本判断是否可继续导航。保存期间产生新编辑时，继续保存到稳定版本，或保留当前编辑器并明确未完成导航；不得无限重试或用旧快照成功来清空新内容。正常自动保存仍可保留脏标交给下一轮，只有离开保护承担阻止替换的职责。
- 普通切章、返回、搜索跳转，以及其他会替换或卸载编辑器的用户导航，必须遵守同一约定；拆书和书写两个长活缓冲均在范围内。连续点击、迟到读取和失败响应必须绑定对象与请求生命周期，不能把旧响应应用到新的编辑器。
- 冲突沿用现有重新加载或明确覆盖的交互，失败沿用保存错误与重试入口。阻止导航时原文字和当前对象保持可见，不新增每次导航的常规确认弹窗，不用强制覆盖消除冲突。
- 更改库位置和新建空库共用一次工作区切换流程：文件夹选择及必要校验完成后，先解决会受切换影响的长活缓冲，再提交当前库偏好与板块状态。选择取消、保存失败或冲突未解决时，保留旧库为当前库。
- 提交切库后，拆书、灵感库、构思、书写、全局搜索、当前项目、继续工作和待处理导航须统一归属新库。旧编辑器退出或重新绑定，新库为空时显示正常空态。恢复入口只能重新打开当前库实际扫描到的对象，不能按另一库的历史路径恢复。
- 各扫描、搜索、读取和跳转响应使用库身份与请求代次约束。无需强制终止不可取消的 IPC，但它们返回后不得再更新当前库的界面、打开对象或发起后续操作。
- 已明确发起且满足保存保护的旧库写入可以完成，不能因切库使其改写新库。切库提交后不得以旧对象发起新的创作写入。书写速记继续使用现有库内项目与章节归属校验；失败时保留便笺草稿，不建立跨库兜底关联。
- AI 会话历史继续保存在原应用状态中。切库后当前文档上下文、编辑器桥和采纳目标须跟随有效的当前对象；不把历史会话删除或搬入新库，也不自动向供应商发送材料。
- 伏笔、期待线及主线里程碑在原 YAML 对象条目上使用独立布尔键“待打磨”；缺失或 false 为普通对象，true 为待打磨，退出时移除该键。前后端读模型暴露该状态，状态操作不修改原有状态机、锚点、所属主线、类别、档位、关联单元或叙事次序。
- 状态切换以现有权威数据为底，只改目标对象的状态键，保留其未知字段、同表其他对象及未知字段。保存继续遵循既有原子写、长活表指纹和读合写边界；不可解析的表或无法安全定位的对象明确拒写。不得把载入旧表后整表覆盖视为单键修改。
- 对象定位必须能区分所属主线及里程碑，并在外部修改或重排时检测陈旧请求；同名里程碑不能仅凭标题定位，不得把旧数组索引误当成可跨修改的身份。定位无法唯一确认时拒绝操作并要求重新载入，优先沿用现有模型和指纹，不为此引入新的全库迁移机制。
- 对应页面复用完整内容表面和待打磨区，便笺仅为状态呈现，不复制业务内容。伏笔的埋设与回收、期待线的类别档位与兑现、里程碑的变化与读者感受、关联单元及备注均按已填内容呈现；缺省业务分组或筛选不能使待打磨对象丢失于顶部区域。
- 保持全局搜索和原有看板读取同一份对象数据。整理完成后返回原分类和次序，空待打磨区整体消失；纯呈现偏好仍存应用状态，业务状态随项目保存。
- 终验采用旧库完整副本与空新库，记录受测代码版本、构建产物、窗口尺寸、执行步骤及结果。交付分开标明自动验证、页面行为和原生实机验证，不用关闭子工单、模拟 IPC 或构建成功替代后两项。

## Testing Decisions

- 用户已确认测试边界：优先在完整页面流程上验证保存后切章、返回、搜索，以及切换库；底层复用现有临时库命令测试验证文件安全、待打磨和兼容性；最终进行 Windows 新旧库与重启终验。
- 好的测试观察作者可见行为、落盘文件和导航结果，不断言组件内部变量、函数调用次数或序列化格式细节。只有“待打磨”键、未知字段保留和文件唯一来源等格式合同直接检查存储内容。
- 优先复用编辑器保存与导航、工作区切换的现有公开边界。若需要新测试接缝，放在页面流程对外部 IPC 与文件选择器的边界，以少量统一测试设施运行真实页面，不新增生产模拟入口，也不复制一套业务状态模型来证明自己正确。
- 保存导航回归通过可控延迟复现：正常保存并切章；保存期间继续输入；已有自动保存正在进行；连续切章；返回项目；全局搜索跳转；拆书导航；保存失败；外部指纹冲突。断言全部新文字落盘后才离开，或者原编辑器仍保留文字并可继续操作，目的地与最新有效请求一致。
- 库切换回归同时预先打开拆书稿、构思对象和书写章节。覆盖选择取消、空新库、已有另一库、保存失败、指纹冲突，以及旧库扫描/搜索/读取迟到。断言库偏好和所有有效对象归属一致；提交切库后旧响应不回填；搜索、继续工作、速记和采纳目标只使用有效的新库对象。
- 迟到响应使用可控 promise 或等价调度，不依赖偶发的磁盘慢速。页面测试验证旧响应返回后的结果，而非只验证取消函数曾被调用。
- 待打磨底层沿用现有 Rust 临时库先例：创建真实文件，经公开操作进入、编辑、退出并重读。分别覆盖伏笔、期待感、目标与里程碑；旧文件无键；false；未知字段；同名里程碑；外部重排或修改；损坏 YAML；失败时原文件保持；没有便笺副本；原分类和次序恢复。
- 待打磨页面回归验证顶部完整内容、进出状态、空区消失、原分组/顺序恢复和搜索定位，避免逐卡截图或字段标签的脆弱快照。已有 Markdown 对象的便笺行为也必须保持。
- A1/A2 的源函数隔离复现是诊断先例，修复的验收门槛是完整页面外部行为回归。不得仅调整复现脚本或内部返回值断言就宣布通过。
- 运行前端全部现有测试、类型检查与生产构建，以及后端完整测试；在实现修复后生成当前 Windows 独立程序与 NSIS 安装包。既有 370/46 的数量是验收基线，新增有效回归可以使数量增长，不把数量固定为通过条件。
- 真实 Windows 终验在旧库完整副本和干净新库各执行六条流程：完整内容卡/待打磨；人物与组织关系画布；地图与地域及方法预览；独立设置与助手预设；编辑器动作及章节总览、速记、搜索、拆章和主动校对；三配色与浅/深/跟随系统切换及独立编辑器背景。
- 两套库均关闭重开，复核正文、布局、固定节点、人工次序、待打磨状态与设置偏好。取消迁移和未采纳方法预览后比较未编辑创作文件内容指纹；旧数据未迁移仍可读取。按既有保存合同处理主动编辑的文件，不要求正常编辑后字节保持不变。
- 在 960×640 和 1280×800 等常见窗口尺寸检查无正文横向阅读滚动、画布可操作空间、键盘可达性、可见焦点和减少动效。真实供应商连通、流式、取消及采纳若未执行，应列为未验证，不能从预设隔离单测推断通过。
- 原生窗口控制不可用时，将实机步骤明确保留为待执行，并交给具备该能力的执行环境或人工验收。编码检查和安装包构建不能冒充双击启动、安装后启动或重启结果。

## Out of Scope

- 新的创作功能、自动写正文、自动剧情安排、评分、计时、热力图、敏感词检查或云同步。
- 把创作文件迁入数据库、另建便笺库、全库格式重写或引入新的世界观模型。
- 从 #54 删除全对象待打磨要求；如以后决定缩小范围，需要新的明确产品决定。
- 为通过验收而强制覆盖冲突、静默恢复损坏 YAML、自动采纳 AI 或方法布局。
- 重设计全部关窗、崩溃恢复或会话存储策略；已有合同仍需保持，不能将导航修复扩成任意失败下的强制写入。
- 常规导航新增强制确认流程、逐卡视觉快照、通用浏览器测试平台建设或纯内部函数覆盖率目标。
- 自动关闭 #54 或 #1、把旧构建产物标为修复版本、仅凭发布本规格就宣称整体完成。

## Further Notes

- 依据为本次《工笔整体验收 · 2026-09-27》、此前《第二轮汇总验收》及 #54 的完整合同。A1/A2 为当前源函数隔离复现确认的问题；原生界面中的完整复现仍应在实施与终验阶段补记。
- 当前本地验收基线为 `wayfinder` 上的 `e3c7f2b660564eea401d7d1a5aa5568292c8d36b`，不假定这些修改已经推送或已进入日常安装包。实施前确认实际代码版本和工作区现状，保留现有改动。
- 顺序为先修复两项数据安全问题并补页面回归，再补齐 YAML 对象待打磨，最后进行整合构建与实机终验。可将实施拆成关联子工单，但子工单通过不能代替总体验收证据。
- 代码修复、页面回归和实机验收都达到合同后，在 #54 补充证据并判断是否可以关闭。实机能力受限时可交付已验证的修复，但必须保持整体终验未完成的准确状态。
