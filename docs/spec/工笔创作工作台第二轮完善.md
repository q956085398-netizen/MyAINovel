# 工笔创作工作台第二轮完善规格

## Problem Statement

工笔已经打通拆书、灵感沉淀、构思与书写的基本链路，但现有界面与数据模型还不能让作者顺畅地理解和操纵一部长篇小说：设置和编辑器动作过于集中；侧栏上挤下空；内容卡只露出标题与摘要，迫使作者不断点开和左右扫视；AI 普通对话无法建立自己的助手预设；人物、组织、地图与地域的模型过薄，画布无法稳定表达和保留作者的空间安排；部分理论虽然存在于文档，却没有转化为可见、可跳过的构思提示；写作页也缺少直接减少中断的搜索、速记、拆章与本地校对能力。

作者需要的是一个以写作本身为中心、能完整看见内容、能在文字与关系画布之间往返、又不会被模板和评分绑住的个人创作工作台。

## Solution

把工笔升级为一个内容驱动的创作工作台：日常管理页采用窄轨侧栏的“编辑部案头”框架，同时保留可展开的当前项目、继续工作与真实待办信息；进入正文后切换到低干扰的沉浸布局。内容对象默认展示全部已填写字段和正文，任何卡片都能进入“待打磨”状态，并以便笺形态集中在页面顶部。

设置改为独立页面；普通 AI 对话获得可由用户创建的 AI 助手预设，但固定命令和人物对话不受影响。构思增加轻量首页、读者遐想、桥段类型—解法、可删的力量体系提示与方法视角。人物、组织、地图、地域升级为一等实体，并分别通过社会关系网与地图结构网形成可拖拽、可保存、可自动整理的语义画布。写作页增加章节卡、关联速记、全局本地搜索、光标拆章与四项主动本地校对，同时明确排除专注计时、热力图和敏感词检查。

## User Stories

1. As an author, I want the main workspace to devote most of the window to my material, so that cards and canvases do not feel squeezed by navigation.
2. As an author, I want the daily management pages to use a narrow navigation rail, so that I can switch sections without sacrificing horizontal space.
3. As an author, I want to expand a current-project area from the narrow rail, so that I can see the active book without permanently widening the sidebar.
4. As an author, I want to resume the last chapter or object I edited, so that returning to work takes one action.
5. As an author, I want the sidebar to show real pending titles rather than only counts, so that the unused lower space helps me decide what to continue.
6. As an author, I want AI and Settings to remain anchored at the bottom of navigation, so that global tools stay predictable.
7. As an author, I want the writing page to reduce navigation prominence, so that the manuscript remains the visual center.
8. As an author, I want the management workspace and writing workspace to share one visual language, so that the mixed layout does not feel like three applications pasted together.
9. As an author, I want content cards to show all filled fields and body text by default, so that I can understand them without opening every card.
10. As an author, I want cards to avoid internal scroll areas, so that I can follow one vertical reading path through the page.
11. As an author, I want to collapse an individual card manually, so that I can reduce density when I choose.
12. As an author, I want search matches to expand collapsed cards automatically, so that a hidden passage never makes a result confusing.
13. As an author, I want inspiration to use an adaptive card wall, so that short and long ideas remain easy to browse.
14. As an author, I want people, organizations, maps, and regions to use complete two-column records, so that comparable entities stay aligned.
15. As an author, I want bridges and units to retain visible narrative order, so that a masonry layout never scrambles sequence.
16. As an author, I want chapter cards to show chapter intent rather than full chapter prose, so that overview remains useful without duplicating the editor.
17. As an author, I want any content object to be marked 待打磨, so that unfinished thinking has one consistent state across the application.
18. As an author, I want 待打磨 objects to appear as complete notes at the top of their own page, so that ideas still ferment in context.
19. As an author, I want finishing a note to return it to its original category and order, so that the temporary state never destroys organization.
20. As an author, I want the 待打磨 section to disappear when empty, so that an unused workflow does not occupy space.
21. As an author, I want the editor header to contain only return, title, save state, and one primary action, so that the top of the manuscript is calm.
22. As an author, I want insertion actions grouped under one menu, so that infrequent commands do not compete with writing.
23. As an author, I want AI actions grouped under one menu, so that fixed commands remain available without dominating the editor.
24. As an author, I want selection-only actions to appear only when a suitable selection exists, so that contextual commands make sense.
25. As an author, I want typography controls collapsed by default, so that detailed formatting remains available without becoming permanent chrome.
26. As an author, I want Settings to be an independent page with 外观、编辑器、AI、库与数据 tabs, so that application preferences have a stable home.
27. As an author, I want provider and model configuration removed from the AI conversation panel, so that the panel focuses on conversations.
28. As an author, I want the conversation selector, new conversation, delete conversation, and collapse action to remain in the AI panel, so that conversation management stays close to the conversation.
29. As an author, I want built-in AI assistant presets for general help, book analysis, ideation, and line editing, so that useful starting points exist immediately.
30. As an author, I want to create an AI assistant preset with a name, description, icon or color, system prompt, and optional provider/model override, so that normal conversations can match my working style.
31. As an author, I want each conversation to retain the preset chosen at creation, so that later preset changes do not silently alter its personality.
32. As an author, I want switching presets mid-conversation to create a new conversation, so that context and behavior do not become ambiguous.
33. As an author, I want assistant presets to affect only normal conversations, so that fixed AI commands remain reproducible.
34. As an author, I want assistant presets not to affect 人物对话, so that a book character continues to speak from book data rather than a global assistant persona.
35. As an author, I want AI settings to explain what material is sent to a provider, so that I can understand the privacy boundary before using a feature.
36. As an author, I want a lightweight 构思首页, so that I can regain the shape of a book without opening every subsection.
37. As an author, I want 构思首页 to show existing summaries and unresolved questions rather than completion percentages, so that it supports thought instead of grading me.
38. As an author, I want “类型圈” presented as “读者遐想（类型圈）”, so that the feature prompts me to think like a reader instead of managing labels.
39. As an author, I want prompts for reader expectations, genre stereotypes, and the book's unique appeal, so that I can explore what the premise implicitly promises.
40. As an author, I want each bridge to record zero or more 类型→解法 pairs, so that I can vary execution under the same reader expectation.
41. As an author, I want an optional power or cultivation-system prompt in worldbuilding, so that progression fiction can expose level boundaries, sources, costs, exceptions, and future expectations.
42. As an author, I want every theory-derived prompt to be deletable and skippable, so that one writer's method never becomes a universal template.
43. As an author, I want techniques such as 千丝万线、莲花 and 千层饼 to be views or layout suggestions over my existing data, so that trying a method does not clone or rewrite my work.
44. As an author, I want adopting a suggested layout to require an explicit action, so that methods never override hand-arranged canvases silently.
45. As an author, I want people to have concise structured facts plus a free-form biography, so that I can scan identity while retaining expressive prose.
46. As an author, I want a person's structured facts to include image, one-line identity, aliases, age or perceived age, gender, traits, current goal, strengths, cost or weakness, and personal secret, so that the full card is useful without becoming a mandatory form.
47. As an author, I want organizations to be first-class project entities, so that factions are more than a string attached to a person.
48. As an author, I want one person to belong to multiple organizations with role, current/former status, public/secret status, and relation type, so that shifting loyalties can be represented.
49. As an author, I want a single 人物与组织 area containing people, organizations, and a relationship canvas, so that social data has one coherent home.
50. As an author, I want people rendered as circles and organizations as rounded rectangles on the canvas, so that node kinds are recognizable without reading every label.
51. As an author, I want to drag a relationship node and find it in the same place next time, so that the canvas reflects my mental model.
52. As an author, I want to pin selected nodes before automatic arrangement, so that cleanup does not erase deliberate placement.
53. As an author, I want one action to arrange only unpinned nodes, so that I can tidy a partially curated canvas.
54. As an author, I want a full relayout action that is undoable, so that I can recover from an unsatisfying automatic layout.
55. As an author, I want relationship cards and the relationship canvas to read the same people, organizations, and edges, so that edits never diverge across views.
56. As an author, I want a map to represent a whole story space and a region to represent a local part inside it, so that the application does not confuse overview with locality.
57. As an author, I want one project to contain multiple maps, so that a long novel can move between major story spaces.
58. As an author, I want a region to expand into another map, so that a previously local place can become a detailed story space without losing its parent context.
59. As an author, I want map pages for 全貌、地域、转场 and 历史, so that spatial, transitional, and historical questions are separated without fragmenting the domain.
60. As an author, I want region connections separated from map transitions, so that a nearby road is not modeled like a major narrative relocation.
61. As an author, I want map cards to show scale, boundaries, global conflict, main line, secrets, and entry/exit conditions, so that the overall space carries story purpose.
62. As an author, I want region cards to show local scale, people, organizations, conflict, secret, and local main line, so that a place is immediately writable.
63. As an author, I want a whole-book map canvas and a single-map region canvas, so that I can reason at two spatial levels.
64. As an author, I want optional overlays for people, organizations, and plot elements, so that the same map can answer different planning questions without duplicating data.
65. As an author, I want to create, connect, drag, pin, edit, and automatically arrange map nodes, so that the canvas is an active semantic view rather than a screenshot.
66. As an author, I want an optional background image behind a map, so that an existing sketch can orient nodes without requiring a drawing engine.
67. As an author, I want existing projects to remain readable before migration, so that upgrading the application never forces an immediate rewrite of my library.
68. As an author, I want a migration preview that lists created and changed data, so that I can understand the conversion before approving it.
69. As an author, I want migration to preserve unknown fields and refuse to overwrite unreadable structured data, so that hand-edited files remain safe.
70. As an author, I want a browsable chapter-card overview, so that I can jump among chapters without turning the overview into another editor.
71. As an author, I want a quick note from the writing page to become a project- and chapter-linked inspiration in 待打磨 state, so that I can capture an idea without leaving the manuscript.
72. As an author, I want Ctrl+K to search projects, chapters, people, organizations, maps, regions, units, bridges, foreshadows, expectations, and inspiration locally, so that retrieval does not require remembering where something lives.
73. As an author, I want to split a chapter at the cursor after reviewing the proposed boundary and new filename, so that an overlong chapter can be divided safely.
74. As an author, I want chapter splitting to be atomic and conflict-aware, so that failure cannot leave half a chapter in two files.
75. As an author, I want local proofreading for unmatched Chinese punctuation, repeated characters or words, custom errors, and proper-name consistency, so that common mechanical mistakes are visible while I write.
76. As an author, I want proofreading to explain and navigate to a finding without changing text automatically, so that final wording remains mine.
77. As an author, I want proofreading rules individually switchable and scheduled so they do not block typing, so that assistance never damages writing flow.
78. As an author, I want no focus timer, streak, heatmap, productivity score, or sensitivity-word checker in the writing workspace, so that the product remains centered on writing rather than surveillance or platform policy.
79. As an author, I want three coherent palettes—朱砂纸墨、竹青松烟、靛青月白—with light, dark, and system modes, so that I can change atmosphere without relearning the interface.
80. As an author, I want editor background selected independently from the application palette, so that manuscript readability can be tuned separately.

## Implementation Decisions

- The management shell uses the B “编辑部案头” structure as its base: narrow navigation rail, wide content surface, and page-level actions close to their content.
- The current-project, resume-work, and real pending-title content from A “书页卡墙” lives in an expandable project-information surface associated with the rail; it does not permanently widen the rail.
- The manuscript editor uses the C “沉浸阅读架” structure: lower navigation prominence, centered writing surface, and a small action hierarchy.
- The three sources define structure, not three independent visual systems. Tokens, control shapes, motion, typography, and interaction rules remain unified.
- Content cards default to full expansion. Collapse state, selected view, and other purely presentational choices are application state; creative content and 待打磨 status remain project/library data.
- 待打磨 is a cross-domain content state. 便笺 is only the visual treatment for that state and does not introduce a second content store.
- Each object's original category and order remain authoritative while it is 待打磨, allowing deterministic restoration.
- Search uses a compact result presentation but exposes full content on demand and expands a matched collapsed object automatically.
- Settings becomes a route-level page with four top-level tabs. Export and publication options remain project-specific and do not move into global settings.
- AI assistant presets are application-level configuration separate from book people, 人物对话, and fixed commands.
- Built-in presets are immutable seeds that can be copied. User presets can be created, edited, deleted, and selected as default.
- A normal conversation stores a stable snapshot/reference of its selected preset behavior. Changing preset starts a new conversation instead of mutating an existing conversation's behavior.
- Fixed AI commands keep their audited prompt and material contracts. No user preset content is prepended or substituted.
- Theory enters the product through three layers: structured data only when relationships/filtering/derived views require it; removable prompts for reflective work; technique cards or method views for non-universal approaches.
- 构思首页 is a read model over existing project data plus dismissible prompts. It stores no duplicate summaries and computes no completion score.
- Bridge 类型→解法 is a repeatable optional structure that uses the shared vocabulary but never validates prose against that vocabulary.
- People, organizations, maps, and regions are first-class file-backed entities. Cards and canvases reference these entities instead of embedding copies.
- Social membership is modeled as an explicit relationship rather than a single group field. A person may have multiple organization relationships.
- The social graph and map graph are separate aggregate roots because they answer different questions and evolve independently.
- Social graph nodes have stable typed identities. Person and organization identities cannot collide merely because their display names match.
- Social graph layout records position and pin state separately from entity content. Moving a node changes only layout state.
- Automatic arrangement has two modes: arrange unpinned nodes while preserving pinned nodes, and full relayout. Full relayout creates one undoable transaction.
- A map is an overall story space and a region belongs to a map. A region may link to a child map without becoming that map's duplicate.
- Region adjacency/local connection and cross-map transition are distinct relation types with distinct fields and presentation.
- Map layout uses the same persistence and pinning rules as the social canvas.
- 千丝万线、莲花 and 千层饼 are non-destructive projections/layout suggestions. Only an explicit “adopt layout” action writes layout state.
- Background map images are attachment references. The application does not provide freehand drawing, shape editing, or cartographic authoring.
- Legacy projects remain readable through compatibility adapters. Migration is explicit, previews changes, preserves unknown fields, and uses conflict-safe atomic writes.
- The existing file-as-source-of-truth and human-confirmation boundaries remain in force. Derived views, indexes, and canvases can always be rebuilt from project data plus layout state.
- Chapter cards are browse-only in the first release. Chapter editing remains in the manuscript editor.
- Quick notes reuse inspiration capture and add project/chapter relationships plus 待打磨 state; no separate note library is created.
- Global search remains local and read-only. It presents typed results and navigates to the authoritative editor or detail surface.
- Cursor split is a previewed transactional operation: validate source version, calculate both results, atomically write the new chapter and updated original, and leave neither partially updated on failure.
- Proofreading contains exactly four rule families: paired Chinese punctuation, duplicate characters/words, user-defined errors, and people/place/proper-name consistency.
- Proofreading emits findings with location, explanation, and optional suggestion. It never automatically edits manuscript text.
- Theme selection combines palette and light/dark/system mode. Editor background remains an independent preference.
- Existing application-level preferences stay outside the creative library; creative entities and relationships remain portable plain text.

## Testing Decisions

- Tests assert externally observable behavior—returned domain objects, files produced, files preserved, conflict errors, migration previews, and navigation outcomes—not internal helper calls, component structure, or CSS class names.
- The primary automated seam is the application command/use-case boundary operating on a temporary creative library. This is the highest existing seam that can prove parsing, validation, atomic persistence, compatibility, and derived read models together.
- Storage tests create realistic old and new projects on disk, invoke the public domain operation, reopen the result, and compare behavior rather than serialized formatting except where the format itself is the contract.
- Migration tests cover: preview without mutation; successful conversion; cancellation; unknown-field preservation; unreadable structured data; name collisions; interruption/failure without partial output; and reopening the old project without conversion.
- 待打磨 tests cover multiple entity kinds, ordering restoration, empty-section behavior at the read-model boundary, and the absence of a second note copy.
- AI tests cover immutable built-ins, user preset CRUD, conversation preset stability, default selection, deleted-preset compatibility, provider/model fallback, and proof that fixed commands and 人物对话 receive no normal-assistant prompt.
- Social-graph tests cover typed identity, multiple organization memberships, directed and undirected edges, secret relationships, invalid references, manual coordinates, pin preservation, deterministic arrange-unpinned behavior, and undoable full relayout.
- Map-graph tests cover multiple maps, region ownership, region-to-child-map expansion, local connections, map transitions, overlays, layout persistence, pin preservation, and method views that do not mutate data before adoption.
- Writing tests reuse existing chapter, search, inspiration, and proofreading precedents. They cover chapter-card scans, linked quick notes, typed global search results, cursor split boundaries, naming collisions, stale source conflicts, atomic failure, and the four approved proofreading families.
- Theme and settings persistence are tested at the preference-service boundary, including palette/mode combinations, independent editor backgrounds, and compatibility with previous saved settings.
- Page-level acceptance tests cover six workflows: card/便笺 browsing, people/organization graph, map/region graph, independent settings, editor action hierarchy, and palette switching.
- Layout acceptance is checked at common Windows laptop widths, with special attention to no horizontal reading scroll, usable canvas space, keyboard reachability, visible focus, and reduced-motion behavior.
- Visual tests compare semantic states and key screenshots only at the page level. Individual card snapshots and token-by-token screenshots are avoided because they are brittle and do not prove user outcomes.
- Existing command-level Rust tests are the prior art for temporary-library integration. Existing library scanning, chapter operations, inspiration persistence, relationship parsing, search, proofreading, and AI-context tests should be extended rather than replaced by new test frameworks.
- Frontend verification includes type checking and production build. Because the repository currently has no browser test runner, automated UI tooling should be added only if it can exercise complete page workflows rather than isolated implementation details.
- Final acceptance includes opening a real legacy library and a clean new library in the Windows application, performing the six workflows, restarting the application, and confirming persisted settings/layouts and unmodified source content.

## Out of Scope

- Immediate implementation of this specification; this issue records the confirmed design and acceptance contract.
- One-click generation of novel prose, automatic plot planning, automatic rewrite without explicit adoption, or AI acting as a judge.
- Focus timers, streaks, heatmaps, productivity rankings, sensitivity-word checking, or platform-policy enforcement.
- A free-form whiteboard, drawing engine, map editor, geographic coordinate system, or automatic cartography.
- Mandatory theory templates, completion percentages, chapter scores, red missing-field warnings, or enforced creative order.
- A separate theory section that reproduces source articles inside the application.
- Multi-user collaboration, mobile-first redesign, cloud synchronization, or generalized publishing-platform integration.
- Drag-to-reorder chapters in the first chapter-card release.
- Full manuscript version diff; existing snapshot recovery remains, and diff returns only if repeated real use demands it.
- Replacing plain-text creative files with a database or storing duplicate business data in canvases.

## Further Notes

- The visual direction is confirmed as B main workspace + A project-information surface + C immersive writing page. The static alternatives were decision aids, not production templates.
- The theoretical material is a source of prompts and perspectives, not a source of universal truth. Product behavior follows the project's existing principle of gradual structure: free prose first; structure only when reliable relationships, filtering, or derived views require it.
- Public transcripts were not available for the three referenced writing-workbench videos. Feature choices based on them are limited to publicly verifiable descriptions and the referenced open-source project documentation.
- Delivery is already decomposed into implementation tickets #47 through #53. This umbrella specification is the cross-ticket contract; a child ticket may narrow scope but must not contradict these user stories or boundaries without a new explicit decision.
- No production application change is authorized merely by publishing this specification.
