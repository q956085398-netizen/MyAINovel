# 参考项目数据模型与交互调研报告

调研时间：2026-09-06。评估基线：ADR 0002「文件为唯一数据源（Markdown+YAML，索引只是缓存，用户可在 Obsidian 里直接改文件）」+ ADR 0001（Tauri 独立应用）+ ADR 0003（AI 只处理人写内容）。

## 一、obsidian-webnovel-assistant（WNA，重点对照）

> 来源：[GitHub 仓库](https://github.com/HatanoChihiro/obsidian-webnovel-assistant)（MIT，TypeScript，184 stars，117 commits）；以下伏笔/时间线格式均直接核对了仓库源码 `src/utils/ForeshadowingParser.ts`、`src/services/ForeshadowingManager.ts`、`src/services/TimelineManager.ts`、`src/utils/preciseTextHighlight.ts`，非仅凭文档推断。

### 1.1 核心数据模型

**数据分三层存储**（这是它对 ADR 0002 最重要的示范）：

| 层 | 存放位置 | 内容 | 性质 |
|---|---|---|---|
| 创作数据 | vault 内 Markdown | 章节正文（frontmatter 含 `status`/`synopsis`/`exclude-word-count`）、`伏笔.md`、`时间线.md`、`限时任务.md`、`设定/` 文件夹（字典大纲） | 唯一数据源，用户可直接改 |
| 应用状态 | `.obsidian/plugins/.../data.json` | 插件设置、每日字数历史、专注/摸鱼统计、便签 | Obsidian 惯例；历史可导出 JSON 备份 |
| 缓存 | `cache-data.json` | 设定引用统计、文件夹字数缓存 | **可随时重建**，有「重建设定缓存」「重建文件夹字数缓存」命令兜底 |

**伏笔条目格式**（从 `ForeshadowingParser.ts` 逐行确认，`伏笔.md` 单文件多条目，`---` 分隔）：

```markdown
## 宝库钥匙的下落

> [[第1章|第1章 初入江湖]] - 2026-08-08 12:00
> 他摸了摸口袋里那把黄铜钥匙，若有所思。

> [[第12章]] - 2026-09-01 20:11
> 钥匙再次出现在酒馆的抽屉里。

**标签**：#道具, #线索
**状态**：未回收

**回收于**：
- [阶段] [[第15章]] - 2026-09-02 10:00：揭露了主角的部分身世线索
  > 回收处的原文引用
- [终结] [[第30章]] - 2026-09-05 21:00

---
```

- 状态机：`未回收(pending) → 阶段回收(partially_recovered) → 已回收(recovered)`，旁支 `已废弃(deprecated)`；「彻底回收」= 追加一条 `stageType: 'final'` 的回收日志。
- 一个伏笔可关联多个章节：埋设引用（`contents` 数组，可多条）与回收日志（`recoveryLogs` 数组）分开存。
- 相同描述的伏笔再次标注时**合并进既有条目**（追加引用块），不产生重复。

**锚点方案（工单关键疑点的答案）——WNA 不在正文中插入任何标记**：
1. 跳转到章节靠 Obsidian wikilink `[[章节名]]`；
2. 精确定位到行靠**引用原文的文本匹配**：`preciseTextHighlight.ts` 把伏笔条目里保存的引文在目标章节文本中做规范化匹配（压缩空白、忽略大小写），命中后做词句级高亮。不用行号（编辑会漂移）、不用 Obsidian `#^` 块锚点（要求用户正文里出现锚点标记）。
3. 代价：正文改写后引文匹配失败则退化为只能跳到文件。

**时间线条目格式**（`时间线.md`，源码+用户指南双重确认）：

```markdown
## 第一天 - 主线
> 主角离开家乡，踏上冒险之旅
**章节**: [[第一章]]
**类型**: 主线
---
```

源码还支持 `- 事件描述 [[章节]] [[章节2]]` 列表形式（一个时间点多事件、多章节关联），以及从选中文字添加时记录来源。默认类型枚举：主线、支线、回忆、伏笔线、暗线。

**设定系统（字典大纲模式）**：`设定/` 文件夹多级子目录；分类文档中 `## 二级标题` = 词条正名，词条正文内 `**别名**：a、b、c`（逗号/顿号/分号/斜杠/竖线分隔）；整份文档无二级标题时以文件名为词条。正文输入正名/别名自动加虚线下划线+悬停速查卡。出场次数与出场章节由缓存统计。

**章节体系**：文件名即序号来源——内置 5 条正则预设（阿拉伯数字/中文数字/纯数字/具名章节/自定义），规则有优先级；拖拽排序时按新顺序**重命名文件**。章节元数据全部在 frontmatter（`status`：待写/大纲/草稿/修稿中/已完稿；`synopsis` 摘要）。

### 1.2 关键交互

- **标注伏笔**：选中正文 → 右键「标注为伏笔」→ 填描述+标签 → 写入 `伏笔.md`（相同描述自动合并）。
- **伏笔看板**：三栏（待回收=未回收+阶段推进 / 已回收 / 已废弃）+ 标签筛选 + 关键词搜索；点卡片 → 打开源章节并高亮引文行。
- **阶段推进/彻底回收**：看板卡片上直接操作，弹窗填说明+选章节；也可把光标放在 `伏笔.md` 条目上执行「标记伏笔已回收」。
- **双向联动**：`buildChapterForeshadowingMap` 把伏笔按章节反向映射，工作台章节卡片底部显示该章的伏笔徽章，点击预览。
- **写作工作台**：6 选项卡（全章节/时间轴/设定/伏笔看板/任务看板/便签）；时间轴支持把章节卡片拖到时间节点绑定事件。
- **自动建章**：按当前文件名识别编号规则递增；**目标文件已存在则直接打开而不重复创建**；多模板可选。
- **合并章节**：整部/分卷合并预览 →（桌面）修订 → 应用回原章节 或 导出。
- **字数三模式**：网文（所有非空白字符含标点，起点/晋江口径）/ 标准（中文逐字+英文按词+全角标点，默认）/ 原生（忽略全部标点）；切换后全库重算；统计排除 YAML、markdown 语法、代码块；增量用「时间戳校验基准+冷启动保护」防跳变；gutter 字数提醒（每 N 字行号区标签）。
- **沉浸模式**：全屏+打字机居中+行淡化+插槽化面板布局。

### 1.3 可借鉴点

1. **「条目自包含 + wikilink 引用 + 引文文本锚定」的伏笔方案整体成立**：正文零污染、数据全在 md、跳转体验够用。工笔可直接采用此思路。
2. 伏笔四态状态机 + `[阶段]/[终结]` 双类型回收日志，精确匹配长篇「逐步揭开」规律。
3. 伏笔↔章节反向映射（章节卡片徽章）是「书写时看见伏笔」的低成本方案。
4. 数据三层分离（创作数据/应用状态/可重建缓存）+ 手动「重建缓存」命令——与 ADR 0002 完全同构。
5. 字数三模式（尤其网文口径）、统计排除规则、防跳变细节、`exclude-word-count` 单章排除。
6. 章节文件名正则规则引擎（预设+自定义+优先级）；自动建章「存在即打开」；合并章节两段式（预览修订→应用回写）。
7. 设定字典大纲（二级标题=词条）+ 别名行内标注 + 虚线下划线，是「Obsidian 里手改文件仍然可读可写」的优秀示范。

### 1.4 不可迁移点 / 教训

1. **正则解析脆弱**：`ForeshadowingParser.ts` 要同时兼容三代历史格式（旧标题式 `## [[章节]]`、`**说明**：` 字段式、新标题式），正则复杂且用手写位置偏移做读改写——工笔无历史包袱，**格式应一次定死、宁严勿宽**。
2. 单文件多条目（`伏笔.md`）在看板高并发读改写下靠 `SerializedWriter` 串行队列勉强保证原子；条目数大时定位与合并成本上升。工笔可考虑一条伏笔一个文件（见综合建议）。
3. 字段用 `**加粗键**：值` 行格式而非 frontmatter——人眼友好但机器解析要靠多语言正则（中/英/i18n 三套键名），工笔应统一用 YAML frontmatter 存结构化字段、正文只存引文。
4. 「点击定位」依赖引文仍存在于正文，正文大改后失效且无提示——工笔可加「引文失配」标记提醒。
5. 它是 Obsidian 插件，沉浸模式/OBS 直播等强绑定 Obsidian API，不可迁移（工笔是 Tauri 自绘编辑器）。

### 1.5 ADR 0002 兼容性：★★★★★（完全兼容）

同为 markdown 存储，其「缓存可重建 + 设置与创作数据分离」就是 ADR 0002 的现成参照实现。最大差异仅在：它把「索引缓存」放在插件目录，工笔的索引缓存位置可自定（应用数据目录），原则一致。

## 二、Campfire Writing — Relationships 模块

> 来源：官方教程 [Relationships Module Tutorial](https://www.campfirewriting.com/learn/relationships-tutorial)（正文从页面内嵌数据中完整提取）、[Systems Module Tutorial](https://campfirewriting.com/learn/systems-tutorial)、第三方评测 [selfpublishing.com](https://selfpublishing.com/campfire-writing-review/)。

### 2.1 核心数据模型

- **Relationship Web（关系网）**：一个 flowchart 画布**元素**；一个作品可建**多个**关系网（如「家族树」「朝堂势力」各一张）；元素本身有名称/描述/缩略图，出现在项目仪表盘等所有引用处。
- **节点（卡片）**：是 Characters 模块中角色元素的**引用视图**，不复制数据；卡片显示角色名+缩略图（来自角色卡），可缩放、自由移动（坐标持久化）。可在画布内「Create New Element」直接新建角色，新建后同时进入 Characters 模块。
- **边（连线）**：从卡片四角节点拖到另一卡片创建；**每条线的中点还有节点，可从线中点继续拉出线**（做家族树/三角关系的关键设计）；线有三种样式（实线/点线/虚线）与方向（箭头/无向）。
- **Relationship Key（关系图例）**：画布级的**可命名颜色值**集合——每种颜色可重命名（如「血亲」「敌对」）、可在箭头/无向间切换、可拖拽排序、可删除（删除颜色不删线，线回退主题默认色）。**分类是有限的枚举值而非自由 RGB**。
- **自动 Links**：被线连接的角色之间自动创建 Campfire 全局 Link（双向引用），角色档案里能看到关系面板。
- 存储：云端+桌面同步的**私有格式，官方未公开 schema（未能核实）**。

### 2.2 关键交互

悬停卡片出四个连接点 → 拖拽连线；右键线改样式/删除；Relationship Key 面板集中管理颜色分类；模块设置含默认线型、Bezier 曲线弯曲度（1-100）。

### 2.3 可借鉴点

1. **「颜色分类 = 可命名的枚举值」**：关系类型不是自由属性而是画布级图例（有限、有序、可命名），一条线挂到某个值上——工笔关系画布照抄这个模型，且枚举值本身可以落到 md 配置文件。
2. **线中点可继续拉线**：家族树/多角关系的结构表达，交互成本低。
3. **节点是引用不是副本**：画布只存「角色 ID + 坐标 + 尺寸」，角色数据在人物卡——与「文件为唯一数据源」天然契合。
4. 一个作品多张关系网（按视角/阵营分图）。
5. 连线自动生成双向 Link（关系出现在双方人物卡上）。

### 2.4 不可迁移点 / 难点

1. **自由画布坐标的持久化**是 md 方案的最大难点（Campfire 闭源无从参考）。WNA 的替代路线：不用自由布局，用力导向自动布局（`ForceLayoutEngine.ts`），坐标不入库——工笔 v1 可先走自动布局回避该问题（见综合建议）。
2. Campfire 是数据库式应用（17 模块共享元素库），无「用户手改文件」诉求，整体架构不可迁移，只有画布模型可借鉴。

### 2.5 ADR 0002 兼容性：★★☆☆☆（仅模型层可借鉴）

存储层私有格式与 ADR 0002 无交集；但「节点引用 + 边挂枚举分类 + 自动双向链接」的模型可用 WNA 已验证的 md 语法落地（`### 关系` 列表或 frontmatter relations 数组）。

## 三、Plottr — 时间线网格

> 来源：官方文档 [Timeline Overview](https://docs.plottr.com/article/54-timeline-overview)、[Plottr Overview](https://docs.plottr.com/article/8-plottr-overview)、[Act Structure 1.0](https://docs.plottr.com/article/67-how-to-use-act-structure-1-0)、[Exporting](https://docs.plottr.com/article/66-exporting)；文件格式佐证 [Gavin Gray 评测](https://www.gavingray.co.uk/plottr-the-novel-plotting-app/)。

### 3.1 核心数据模型

- **网格 = 列（Chapter Headings）× 行（Plot Lines）**。列无上限，标题可自定义语义（章、幕、beat、场景、情节点皆可）；行（情节线）无上限、每线一色、整行可拖拽排序。
- **Scene Card** 落在「章 × 线」交换单元格，每格可多张；卡片字段：标题、描述、图片、超链接、颜色、**自定义属性（Custom Attributes）**。
- 卡片可**链接** Characters / Places / Tags 模块中的已有实体（不能在卡内新建）；链接用于筛选。
- **Act Structure 1.0**：最多三层的嵌套结构（如 幕→章→场景）叠加在网格上。
- 存储：`.pltr` 单文件 = **JSON**（Gavin Gray 实测确认），官方不公开 schema；社区存在第三方 Scrivener→Plottr 转换脚本。

### 3.2 关键交互

三类对象（列/行/卡片）全部拖拽重排；**Flip** 一键水平/垂直翻转时间线；Zoom 缩放；**Filter**：按链接的角色/地点/标签、颜色、自定义属性筛选网格（用于查某角色断档、情节漏洞）；Save as Template 把整张时间线存为可复用模板；导出 MS Word / Scrivener。

### 3.3 可借鉴点

1. **「行=情节线、列=卷/章、格=情节点」的多线并行视图**正是网文多线叙事（主线/支线/感情线/暗线）排布的天然形态，工笔构思板块的「大纲排布」可用此网格作为**视图**，数据仍落到 md（情节点=文件，线与章=frontmatter 属性）。
2. 卡片链接实体 + 按实体筛选网格（查角色 A 在哪些情节点出场）——与 WNA 的「出场章节统计」同功，但网格可视化更强。
3. 情节线颜色=行级属性（区别于 Campfire 的边级颜色）。
4. 时间线存为模板（三幕式、英雄之旅等结构模板复用）。
5. 三层结构（幕/章/场景）映射工笔的 卷/章/场景 层级。

### 3.4 不可迁移点

1. 网格强依赖「格子里放对象」的心智模型，纯 md 落地时**格子位置不是数据**（行/列由属性推导），拖拽卡片跨线/跨章=改属性，需要设计好「排序即改文件序号/属性」的写回策略（WNA 的「拖拽后重命名文件」是已验证的先例）。
2. 单文件 JSON 数据库（.pltr）整体不可迁移（违背 ADR 0002）。
3. 无正文编辑能力（纯大纲工具），与工笔「书写板块」无重叠。

### 3.5 ADR 0002 兼容性：★★★☆☆（交互可借鉴，存储不可）

网格只能作为**派生视图**：从各情节点的 md 文件 frontmatter（`line: 主线`、`chapter: 第12章`、`order: 3`）聚合渲染；拖拽操作写回文件属性。

## 四、Obsidian Longform 插件

> 来源：[kevboh/longform](https://github.com/kevboh/longform) README 与 [docs/COMPILE.md](https://github.com/kevboh/longform/blob/main/docs/COMPILE.md)（均直接核对了仓库原文）；[Projects & Drafts 2.0 重构 issue #35](https://github.com/kevboh/longform/issues/35)。

### 4.1 核心数据模型

- **项目发现**：扫描全库 frontmatter 含 `longform` 键的笔记——该笔记即 **Index File（项目脊柱/目录）**。无中央数据库，项目=「一个文件夹 + 若干场景笔记 + 一个索引笔记」。
- **多场景项目**：每个 scene 是独立 md 笔记；索引文件 frontmatter 中 `scenes:` 为**有序列表**，列表缩进表达嵌套分组（父场景/文件夹结构）：

```yaml
longform: ...
scenes:
  - The Sun Rises on Dublin
  - 第一章
    - 1.1 破晓
    - 1.2 集市
```

- **单场景项目**：短篇=单笔记（frontmatter 声明自身）。
- **Drafts**：同标题的多个项目自动分组为同一作品的不同草稿；`draftTitle` 属性命名。
- **安全原则（README 原文）**："Longform 永不改动你的笔记内容，唯一重写的文件是项目的 index file"——项目结构坏了最多重建索引，正文不可能丢。
- **Compile 模型**：workflow = steps 有序组合，**严格三段**：任意数量 **Scene steps**（逐场景变换，如 Prepend Title/Strip Frontmatter）→ **恰好一个 Join step**（拼接，如 Concatenate Text）→ 任意数量 **Manuscript steps**（整体变换，如 Remove Links → Write to Note）。步骤可带 Text/Boolean 选项；支持**用户 JS 脚本步骤**（`compile(input, context)`，input 为 scenes 数组，含 path/name/contents/metadata/indentationLevel）；workflows 是 **vault 级共享**（改一处全项目生效）。

### 4.2 关键交互

侧边栏三选项卡（Scenes/Project/Compile）；场景列表可拖拽重排与缩进；字数统计与每日写作目标；`.longform-leaf` CSS 类实现「仅写作视图」的主题隔离。

### 4.3 可借鉴点

1. **「结构即一份 frontmatter 列表 + 内容文件永不被自动改写」**——与 ADR 0002 的精神完全一致，建议把这条安全原则原文写进工笔的设计共识。
2. 支持**用户手改 YAML**（README 警告易 desync，但保证「frontmatter 正确时重启即可完全重建状态」）——这正是工笔「索引重建策略」工单需要的行为契约：索引永远可从文件推导，文件永远不被反写破坏。
3. **Compile 三段流水线**（scene→join→manuscript + 用户脚本步骤）是「正文导出/发布格式」（地图 Not yet specified 项）的成熟模型：网文发布=strip frontmatter→去 wikilink→拼接→按平台排版，恰好是一条 workflow。
4. 场景缩进=结构层级（1、1.1、1.2 编号在编译时推导）。
5. Drafts 以「同标题」聚合的轻量做法。

### 4.4 不可迁移点 / 教训

1. `scenes` 列表存**文件名**，重命名场景要同步改索引——desync 高发区（社区论坛有项目消失的求助帖）。工笔若用「索引存路径/ID+启动校验+自动修复」可避免。
2. 索引是单个 YAML 键，多人/多设备同步冲突面集中；工笔纯个人使用影响小。
3. Compile 的 JS 用户脚本生态依赖 Obsidian 环境，工笔若做等价物需要自己的脚本安全边界（可与 ADR 0003 的 AI 边界统一考虑）。

### 4.5 ADR 0002 兼容性：★★★★★（完全兼容，且是「索引只是缓存」的最佳实践样本）

## 五、Writeathon（写拉松）

> 来源：官方指南 [卡片写作](https://guide.writeathon.cn/help/non-linear/card-writing.html)、[卡片盒](https://guide.writeathon.cn/help/arrange/slip-box.html)；[知乎官方介绍](https://zhuanlan.zhihu.com/p/607897505)、[少数派实战](https://sspai.com/post/71071)。

### 5.1 核心数据模型

- **层级**：空间（多空间数据隔离）→ 笔记本 → 故事 → 文章（线性写作）；**卡片是与故事平行的独立灵感库**。
- **卡片**：标题、正文、多级标签、颜色、**层级**（父子卡）、双向链接；多渠道快速创建（App 速记、语音、微信输入、微信读书划线批量导入、拍照识别）。
- **卡片盒（核心创新）：「先有标签，后有卡片盒」**——卡片盒不是物理文件夹，而是**保存的查询条件**（smart folder）：四种抓取条件（卡片时间：动态区间如"最近一周"/静态区间；标签：多选；关键字：全文含行内标签；颜色），满足即自动入盒；**一张卡片可同时存在于多个盒**（A面/B面）。
- **卡片组合**：卡片写作模式=右侧按标签/盒/搜索筛选 → 拖拽选卡排序 → 「生成文章」（卡片按序拼接成文）；卡片拓展模式=单卡层级自动映射为文章的一、二、三级标题；白板=卡片摆桌自由组合，框选进入卡片写作；魔法文章（Pro）=AI 平滑拼接。
- 存储：云端服务（私有格式，**未能核实**导出格式细节）。

### 5.2 关键交互

卡片瀑布流多选批量操作；颜色标记+置顶；卡片→文章的「筛选-排序-生成」三步组合流。

### 5.3 可借鉴点

1. **查询式分组（卡片盒）**对工笔灵感库极有价值：灵感卡片以**标签+属性**组织（文件平铺或按日期归档），「故事卡分类视图」是保存的查询而非物理目录——避免「一张卡该放哪个文件夹」的归类负担，天然支持一张卡被多个词表/项目引用（正好服务 issue #1 的「类型/解法词表+灵感库」单一通道）。
2. **卡片组合成文**是「故事卡转生接口」（已授权工单）的现成交互范式：筛选→拖序→生成草稿。
3. 卡片层级→文章标题层级的映射。
4. 多渠道快速捕捉（对应工笔：全局快捷键速记灵感卡）。

### 5.4 不可迁移点

1. 云端账号体系、多空间，与纯个人本地工具无关。
2. 卡片与故事深度耦合的 UI（App/微信），只有数据模型思想可取。
3. AI 拼接（魔法文章）与 ADR 0003「AI 只处理人写内容」的边界需工单层面另行确认。

### 5.5 ADR 0002 兼容性：★★★★☆（模型可落地）

卡片=一个 md 文件（frontmatter：标签/颜色/层级/链接）完全可行；卡片盒=一个「查询描述」文件（或配置），属于索引层。

## 六、对工笔设计的综合建议

按对工笔的直接影响排序。前四条建议进入 `docs/spec/` 设计时直接采纳，后几条供对应工单引用。

### 6.1 伏笔：采用 WNA 的「正文零污染」锚定方案，但格式更严格

- **正文不插任何标记**。伏笔数据独立成文件；跳转 = 章节链接 + 引文文本匹配高亮；引文匹配失败时在看板上显示「引文已变动」提醒（WNA 缺失的一环）。
- 状态机直接沿用：`未回收 → 阶段回收(N 次日志) → 已回收` + `已废弃`；回收日志区分 `[阶段]/[终结]`。
- 与 WNA 不同，建议**一条伏笔一个文件**（`伏笔/<编号-slug>.md`）：frontmatter 存 `status/tags/埋设章节列表/回收日志数组`，正文存引文引用块与自由备注。理由：工笔是自有格式无兼容包袱；单文件多处目读改写的并发风险（WNA 靠 SerializedWriter 压着）天然消失；用户在 Obsidian 手改单条伏笔更安全；看板=索引聚合。WNA 的单文件方案只在「伏笔总数 <100 且以顺序浏览为主」时更优。
- 伏笔↔章节反向映射（章节卡片显示伏笔徽章）应做——它是书写板块「正文与大纲/伏笔联动」的最小实现。

### 6.2 全局数据分层契约（写进设计共识）

按 WNA 的三层 + Longform 的安全原则固化：

1. **创作数据**：只存在于 Markdown+YAML。含正文、伏笔、时间线、人物/设定、灵感卡、情节线定义。用户可在 Obsidian 直接编辑。
2. **索引缓存**：任何可从创作数据推导的东西（设定引用统计、字数缓存、关系图、看板聚合、画布自动布局）。损坏/缺失时「重建索引」一键恢复，且**重建必须是无损幂等操作**。
3. **应用状态**（WNA 的 data.json 对应物）：编辑器布局、专注计时、每日统计历史、应用设置。放 Tauri 应用数据目录，不进创作目录。
4. **写回铁律**（Longform 原则的工笔版）：*应用对创作文件的写入仅限用户明确发起的编辑动作；索引重建永不修改创作文件。*

### 6.3 人物关系画布：模型抄 Campfire，落地抄 WNA，v1 不存坐标

- 模型：节点=人物文件的**引用**（不复制数据）；边=显式关系，挂**可命名的枚举分类**（Campfire 的 Relationship Key 思路：分类列表本身是一份配置文件，有序、可命名、绑定样式）；另设「自动提及关系」为虚线层（WNA 的自动关联提及），两层分开开关。
- 落地语法沿用 WNA 已验证的两件套：人物词条内 `### 关系` + `- **关系名**: 目标1, 目标2` 列表（或等价的 frontmatter relations 数组，二选一，不要两套并存）。
- **v1 用力导向自动布局、不持久化画布坐标**（WNA 路线），回避「坐标存哪」与 ADR 0002 的冲突；若后续确需手动布局，坐标进索引缓存（丢失=回到自动布局，可接受），绝不进人物文件。
- 连线自动在对方人物卡生成反向链接（双向 Link）。

### 6.4 构思排布：Plottr 式网格作为派生视图

- 「行=情节线、列=卷/章、格=情节点卡片」的多线网格作为构思板块的排布视图；情节线是**定义文件**（名称+颜色+排序），情节点是 md 文件（frontmatter：所属线、所属章、序号、摘要）。
- 拖拽写回策略参考 WNA 拖拽重命名先例：拖动改变 frontmatter 属性（线/章/序号），不动正文。
- 筛选（按人物/标签/颜色过滤网格）与 WNA 的出场统计互补，用于断线检查。

### 6.5 章节/书写：直接吸收 WNA 的成熟细节

- 章节元数据进 frontmatter（`status`/`synopsis`/`exclude-word-count`）；文件名正则规则引擎（内置中文数字/阿拉伯数字/纯数字预设+自定义+优先级）——网文场景必需。
- 自动建章：编号递增 + **已存在则打开** + 多模板选择。
- 合并导出：预览→修订→应用回原章节/导出 两段式。
- 字数统计三模式全收（网文口径为主打），统计排除 frontmatter/markdown 语法；`exclude-word-count` 单章排除；增量防跳变（时间戳基准校验）。
- 时间线沿用 WNA 条目流格式即可（`## 时间点` + 事件列表 + 类型 + 章节链接），但结构化字段建议 frontmatter 化。

### 6.6 灵感库与故事卡转生：Writeathon 的查询式分组 + 组合成文

- 灵感卡=一个 md 文件（frontmatter：标签/颜色/来源），**物理上平铺或按日期归档，不做分类文件夹**；「分类」=保存的查询（卡片盒），支持标签/关键词/颜色/时间组合。
- 「故事卡转生接口」（已授权工单）采用「筛选→拖序→生成」三步组合流，产出的是**人可编辑的草稿文件**（与 ADR 0003 一致：AI/程序只产草稿，人拍板）。

### 6.7 导出/发布：Longform 三段流水线

正文导出（起点后台等渠道）用 scene→join→manuscript 三段式 workflow 建模：去 frontmatter→去 wikilink/伏笔标记→拼章→按平台排版。步骤可配置、可保存为渠道模板（对应 Plottr 的 Save as Template）。

### 6.8 两个必须正视的风险

1. **「手改文件」的容错解析**：Longform 的教训（手改 YAML → desync → 项目消失求助帖）说明：格式宽容度、启动校验、坏条目隔离（跳过+提示而非崩溃）是「文件为唯一数据源」的必修课，建议与「索引重建策略」工单合并设计。
2. **中文正文的引文锚点鲁棒性**：WNA 引文匹配做了空白/大小写规范化，但中文改写一字即失配。工笔可补充：失配时按章节+相似度（如编辑距离阈值）提示最近位置，或允许伏笔条目记录多个引文版本。
