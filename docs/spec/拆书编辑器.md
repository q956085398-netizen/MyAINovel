# 拆书编辑器 · 渐进边界

> 工单 #11 决议（用户已授权代理给最优解，事后否决即可）。
> 基线（设计共识 §四）：渐进式模板非填空表单；插入块五件套；Ctrl+Enter 开下一章；必填仅书级四项＋每章梗概＋桥段类型。本文件画「渐进的度」的边界，供 #13（yaml schema）收口引用。

## 决议

### 章梗概：自由文本，长在正文里

- **不结构化**（不拆事件/人物/钩子字段）：拆书例子「第一章. 点明主角身份，简写世界背景；……」证明分号串联的长句已是自然习惯；结构化留给将来 AI 梳理（从自由文本抽取，人确认——正好落在 ADR 0003 的 AI 边界内）。
- **位置约定**：每章标题后的第一个自然段即该章梗概，多个要点用分号串联。与内容同处、随章移动、Ctrl+Enter 流程顺手；拆书例子那种全书串联清单是**派生视图**不是存储形态，将来要看得见再说。
- **不进 yaml**：yaml 里再存一份梗概必然双源漂移。#13 依此定：v1 yaml 不设章列表，章锚点（序数/标题/行号）一律打开时从正文现算（现状即是）。
- **应用不校验「每章梗概必填」**：必填是拆书纪律，不是表单约束。覆盖率检查靠肉眼翻正文（或将来做只读统计），不靠拦截。

### 章节拍标注：v1 判死不收

- 既不做章级标签，也不做拍内位置标注。
- 理由：
  1. v1 拆书结构化的主线是桥段类型/解法——那是跨书检索的检索面。拍是节奏分析维度，机器聚合的价值要等标注量起来（与「统计图表等积累到几百个再议」同一先例，设计共识 §五）。
  2. 拍标注必须挂在章列表上，而上一条刚定了 v1 yaml 无章列表；为拍单开章列表不值得。
  3. 拆书学节奏的目的用手写就能达成：「这章全程拉扯」写进梗概或点评，自由文本天然承载。
- **复活信号**：当梗概/点评里频繁手写拍名（代入/拉扯/兑现……）时，说明该结构化了。届时形态优先「章级标签」（yaml 章列表随拍一起引入），**不做拍内位置标注**——拆书粒度到章已够，拍内定位是书写期的事。

### 出场人物块：纯文本＋首行约定

- v1 保持纯文本插入块（现状），立一个**书写约定**：块内第一行＝人物名清单（顿号分隔），其后各行自由备注。
- 不做人物名链接/结构化字段：应用内没有人物页实体（「角色」要等 v2 人物关系画布定稿），Obsidian 的 `[[ ]]` 链接在应用内无承接。人物画布落地后再考虑联动——届时首行约定直接升格为解析层，存量文本不废。
- 「人物出场章分布」聚合 v1 不做，先攒数据：块的解析规则将来很简单（扫 `[!出场人物]` 块 → 首行切名 → 映射所在章序数），约定在、数据在，视图随时可加。

### 事件发展结构树：v1 判死，且不承诺 v2 形态

- 它的价值＝全书事件层级视图，而其原料（桥段序列＋章梗概）v1 都已有更基础的承载；真要看层级，markdown 标题大纲（Obsidian 大纲面板）够凑合。
- 若将来复活，正确形态大概率不是「树」而是**桥段时间线**（yaml 桥段列表已有起止＋类型，按序铺开即线）——那属于书库统计图表一族，同受「几百个桥段再议」约束。

### 渐进的判据

- **总则：字段升必填，必须先证明它能回答一个用户真的问过的问题。** 必填集永远＝「最小可用检索集」（当前＝书级四项＋章梗概＋桥段类型），完备性不构成理由。
- **升（可选→必填/结构化）的信号**：同一信息在自由文本里被反复手写（点评里反复写拍名→拍该结构化）；某个检索/统计因缺字段而做不到（想按人物筛→出场人物块该解析）。
- **降/删的信号**：字段连续几本书零使用（yaml 里一直空的键）；或填写打断心流、总是被跳过。
- **机制**：v1 不做使用统计，靠人事后翻 yaml 复盘——文件为源的好处是空键一眼可见；将来的「字段使用率」看板也只是读文件的派生视图。

## 对其他工单的影响

- **#13（拆书 yaml schema）**：v1 yaml 无章列表（章梗概在正文、章节拍不做、章锚点现算）；桥段条目维持 起/止/类型/解法 四键，不加点评/关联 id（见该 spec 的理由）。
- **v1 代码**：无增量——本工单全是「不做什么」的边界，既有五件套/前缀推进/桥段面板已与决议一致。
